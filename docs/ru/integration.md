# Интеграция с Agile и Waterfall

[English version](../en/integration.md) · [← К фреймворку](../../README.ru.md)

VeriFirst не заменяет Scrum, Kanban или Waterfall. Модели управления отвечают на вопрос «в каком порядке и когда делать работу». VeriFirst отвечает на вопрос «как принять результат, сделанный с ИИ, и не пропустить ошибку». Он работает на уровне единицы работы, поэтому встраивается в любую модель.

---

## Scrum

| Элемент Scrum | Что добавляет VeriFirst |
|---|---|
| User story + acceptance criteria | Контракт намерения: к критериям добавляются Границы («что нельзя выдумывать») и способ проверки |
| Definition of Ready | История не готова, если нет проверяемого критерия готовности |
| Definition of Done | Для 🟡 и 🔴 задач обязателен пройденный проход «Сломай» |
| Refinement / планирование | Каждой истории назначается квадрант Карты доверия; ёмкость спринта учитывает время на проверку |
| Velocity | Дополняется TTV и долей ускользнувших ошибок |
| Ретроспектива | Разбор ускользнувших ошибок: на каком шаге цикла их должны были поймать |

### Пример: интернет-магазин, расчёт скидок

Команда из пяти человек, спринт две недели. История: «Как покупатель, я хочу видеть итоговую цену с учётом промокода и накопительной скидки».

**Refinement.** Ошибка в расчёте цены = прямые деньги, но код покрывается тестами → квадрант 🟡. Команда пишет Контракт намерения:
- *Критерий готовности:* 15 эталонных корзин из таблицы бизнес-аналитика дают ровно ожидаемые суммы; скидки не суммируются выше 30 %.
- *Границы:* не менять модуль оплаты; не придумывать поля API промокодов, брать только из `promo-api.yaml`.
- *Проверяющий:* автотесты + ревью другим разработчиком.

**Планирование.** Раньше историю оценили бы в 3 дня разработки. Теперь: 0,5 дня на генерацию кода с ИИ + 1 день на тесты, проход «Сломай» и ревью. В план спринта закладывается именно проверка.

**Сделай — Сломай.** ИИ пишет код за час. Отдельная сессия с промптом «найди ошибки» находит, что при пустой корзине и промокоде функция возвращает отрицательную сумму. Исправлено до ревью.

**Ретроспектива.** Через неделю на проде всплыло, что ИИ использовал поле `promo.expires_at`, которого нет в API. Ошибка ускользнула. Разбор: проход «Сломай» не сверял код с `promo-api.yaml`. Решение: в чек-лист команды добавлен пункт «все поля внешних API сверены со спецификацией», запись D-014 в Журнале решений.

## Kanban

Между «В работе» и «Готово» появляется колонка **«Проверка (Сломай)»** со своим WIP-лимитом. По теории ограничений именно она становится узким местом при работе с ИИ, и доска делает это видимым.

### Пример: служба поддержки

Поддержка из шести операторов готовит ответы клиентам с помощью ИИ.

```
Новые → Черновик ИИ → Проверка (WIP 5) → Отправка (человек) → Закрыто
```

- Типовые вопросы («как сменить пароль») — 🟢: проверяется каждый десятый черновик.
- Возвраты денег и жалобы — 🟡: каждый черновик проверяет старший оператор.
- Отправка клиенту — всегда R3: кнопку «Отправить» нажимает человек.

Через неделю колонка «Проверка» постоянно забита: 20 карточек при лимите 5. Вместо того чтобы снять лимит, команда переводит задачи в лучший квадрант: для 12 частых типов возвратов пишет эталонные ответы, ИИ подставляет в них данные заказа, а проверка сводится к сверке трёх полей. Очередь падает до 4 карточек.

## Waterfall и V-модель

V-модель изначально построена на том, что каждому уровню создания соответствует уровень проверки. Проход «Сломай» — это и есть независимая верификация, а шлюзы обратимости совпадают со stage-gates.

| Фаза | Где ИИ | Квадрант | Проверка |
|---|---|---|---|
| Требования | Черновики разделов ТЗ по стенограммам интервью | 🟡 | Каждое требование сверяется с источником в стенограмме; заказчик подписывает |
| Проектирование | Варианты архитектуры | 🔵 → 🔴 | ИИ предлагает варианты, архитектор выбирает и фиксирует в Журнале решений |
| Реализация | Код, миграции | 🟡 | Тесты, ревью |
| Испытания | Генерация тест-кейсов из ТЗ | 🟡 | Трассировка: каждое требование покрыто хотя бы одним тест-кейсом |
| Ввод в эксплуатацию | Инструкции пользователей | 🟢 / 🟡 | Выборочная проверка на реальном пользователе |

### Пример: ТЗ на внедрение системы документооборота

ИИ за день собрал из 14 стенограмм интервью черновик ТЗ на 60 страниц. Без VeriFirst его бы просто отдали заказчику. С ним:

1. **Контракт намерения** требовал ссылку на стенограмму для каждого требования.
2. **Проход «Сломай»** нашёл 9 требований без ссылки. Шесть из них ИИ «додумал» по аналогии с типовыми системами, заказчик их никогда не озвучивал.
3. Перед **stage-gate «подписание ТЗ»** (R3, необратимо: дальше смета и договор) руководитель проекта лично прошёл по спорным требованиям с заказчиком.

Итог: 2 дня вместо 3 недель ручной работы, и ни одного требования, которого заказчик не говорил.

## Гибридные модели

Работают так же. Частый вариант — Waterfall на уровне контракта с заказчиком и Scrum внутри фазы реализации. Шлюзы обратимости встают на границах фаз, а Карта доверия и «Сделай — Сломай» работают внутри спринтов.
