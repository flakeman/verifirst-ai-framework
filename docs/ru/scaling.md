# Масштабирование: от команды до компании

[English version](../en/scaling.md) · [← К фреймворку](../../README.ru.md)

Логика как в SAFe: команда → группа команд → портфель. На каждом уровне те же шесть компонентов, но с другим содержанием.

| Компонент | Команда | Несколько команд (аналог ART) | Портфель / компания |
|---|---|---|---|
| **Карта доверия** | Квадрант для каждой задачи | Общий каталог типовых задач с заранее назначенными квадрантами | Аппетит к риску: какие квадранты разрешены в каких доменах |
| **Контракт намерения** | Для задачи | Для интерфейсов между командами | Для ИИ-инициатив: цель, критерий успеха, что недопустимо |
| **Сделай — Сломай** | Отдельный проход | Перекрёстная проверка: 🔴 результат одной команды проверяет другая | Независимый аудит критичных ИИ-систем |
| **Журнал решений** | Проектный | Общий журнал межкомандных решений | Реестр ИИ-решений для руководства и регуляторов |
| **Обратимость** | Договорённость в команде | Единая классификация систем по R0–R3 | Корпоративная политика автономии ИИ |
| **Метрики** | TTV, переделки | Ускользнувшие ошибки по командам и на стыках; ёмкость проверки на инкремент | Тренд ускользнувших ошибок, доля затрат на проверку, инциденты |

## Уровень нескольких команд

### Новые элементы

- **Ответственный за проверяемость** (аналог системного архитектора в SAFe). Ведёт общий каталог Карты доверия и классификацию R0–R3, следит, чтобы проверка не стала узким горлом всего потока.
- **Долг проверки** (аналог технического долга). Результаты ИИ, принятые без положенного прохода «Сломай» ради скорости. Его учитывают явно и гасят, иначе он превращается в ускользнувшие ошибки.

### Пример: три команды в банке

*Условный пример.* Мобильное приложение, бэкенд и аналитика данных делают общий продукт — кредитную карту.

**Общий каталог Карты доверия** (одна страница на все команды):

| Тип задачи | Квадрант | Кто проверяет |
|---|---|---|
| SQL-отчёт для внутренней аналитики | 🟡 | Контрольные суммы + аналитик |
| Текст push-уведомления клиенту | 🟡 | Редактор + юрист для промо |
| Код API | 🟡 | Контрактные тесты + ревью |
| Логика кредитного скоринга | 🔴 | ИИ только советует; решение — риск-менеджмент |

Без каталога мобильная команда считала тексты уведомлений 🟢, а юристы узнавали о них из жалоб клиентов.

**Контракт на интерфейсе.** Бэкенд с помощью ИИ генерирует новый API лимитов. Контракт намерения между командами: «формат ответа соответствует `limits-api.yaml`, сумма лимита никогда не приходит отрицательной, при ошибке код 503, а не 500». Проход «Сломай» делает мобильная команда — потребитель API, а не автор.

**Долг проверки.** Перед релизом бэкенд принял 12 результатов ИИ без прохода «Сломай», чтобы успеть. Это записано как долг: 12 карточек в бэклоге с меткой `verification-debt`. На планировании следующего инкремента на их погашение заложено 3 дня. Два из двенадцати оказались с ошибками.

**Планирование инкремента (аналог PI planning).** Каждая команда указывает не только объём работ, но и ёмкость проверки: часов ревьюеров в неделю. Если команды вместе планируют больше 🟡 и 🔴 задач, чем могут проверить, лишние переносятся до планирования, а не всплывают в конце.

## Уровень портфеля / компании

Здесь фреймворк фактически становится системой управления рисками ИИ.

### Пример: корпоративная политика

*Условный пример* политики на одну страницу:

1. **Аппетит к риску по доменам.**
   - Маркетинг, внутренние документы: разрешены все квадранты.
   - Работа с клиентами: 🟢 запрещён, минимум 🟡.
   - Финансы, право, персонал: ИИ только в режиме 🔴 «Советуйся».
2. **R3-действия, всегда требующие человека:** отправка внешним адресатам, платежи, изменение данных клиентов, подписание, выкатка в прод, удаление данных.
3. **Реестр ИИ-решений:** каждая система с ИИ, влияющая на клиентов, имеет владельца, квадрант, способ проверки и журнал решений.
4. **Квартальный отчёт правлению:** число ускользнувших ошибок по доменам, доля затрат на проверку, инциденты и их разбор.

### Связь с внешними требованиями

Портфельный уровень удобно сопоставить со стандартом ISO/IEC 42001 (система менеджмента ИИ) и европейским AI Act. Такое сопоставление требует сверки с первоисточниками и готовится отдельным документом.
